**3. Responsibilities**

The requirement is not atomic. It decomposes into three responsibilities.

- **Sample on schedule.** Fire every five minutes and obtain the supplied queue length.
- **Evaluate the rule.** Compare the number with the configured threshold.
- **Conditionally dispatch.** When the rule fires, send exactly one alert through the existing notification service.

**4. Routing decisions**

- **Sample on schedule: deterministic code.** A timer trigger and a read of a supplied value. No content changes what happens next.
- **Evaluate the rule: deterministic code.** A numeric comparison against a configured value is a fixed rule. A model would only add uncertainty to arithmetic.
- **Conditionally dispatch: deterministic code.** A fixed conditional call to an existing service, plus whatever state enforces "one alert". No interpretation is involved.
- **Workflow axis:** a fixed scheduled sequence. The timer is the only orchestration needed. A separate workflow engine is not justified by this sequence. Retry and idempotency around the send are workflow concerns that deterministic code owns, and whether they are required is an open question.

**9. Authority chain**

Sending an alert is a consequential operation. It reaches people. The chain is explicit below.

1. **Reasoning:** none by a model. A fixed rule produces the alert proposal.
2. **Authorization and policy control:** the configured rule defines the condition. Whether that rule also constitutes dispatch authority, and what suppression policy defines "one alert", is *unknown — governance decision required*. A configured destination alone is not dispatch authority.
3. **Authoritative service:** the existing notification service. Identity and owner unknown.
4. **Execution:** the send call, only after the control check passes. An idempotency key per breach episode would enforce "one alert". That is a hypothesis, not a stated requirement.
5. **Audit:** a record of every evaluation and every dispatch, including suppressed ones. Owner unknown.

**10. Generic mechanism and product delegation**

Generic mechanism: a scheduled deterministic job. A timer trigger, a numeric comparison, a conditional call to the existing notification service, and a small piece of state for alert suppression. No AI mechanism of any kind.

The maf-architecture-mapping skill is installed, but there is no agent or AI construct to map. Scheduler and hosting product choices sit outside this router and are not asserted from memory. The analysis stops at the generic mechanism.

**11. Rejected alternatives**

- **All-deterministic:** sufficient. This is the chosen routing.
- **Bounded-AI-only:** could return the comparison, but adds cost, latency, and non-zero error to a rule that arithmetic gets right every time.
- **Agent-everywhere:** could perform the comparison and the send, but grants a model dispatch discretion the requirement never asked for.
- **Multi-agent:** no distinct security, context, deployment, ownership, model, or specialisation boundary exists, so a second agent adds only coordination.
- **Workflow-only:** sufficient. A fixed comparison and service call inside a scheduled sequence is exactly what a workflow with deterministic activities does, and a timer alone already covers it.

**12. Decisions, evidence, trade-offs, assumptions, open questions**

- **Decision:** three responsibilities, all deterministic code, on a five-minute timer, calling the existing notification service. No agent, no bounded AI, no MCP boundary.
- **Evidence relied on:** the requirement text at rung 4 and the counter-example precedent at rung 4. All run-time evidence rungs above are stated, not observed.
- **Trade-off accepted:** the job cannot adapt to a novel situation, such as a stale metric or a flapping queue. That is the correct trade. Adaptation was not requested, and predictability is the value here.
- **Assumptions, labelled:** the queue length is available at each tick as a single number. Suppression state for "one alert" is a hypothesis pending the governance answer.
- **Open questions:** the semantics of "one alert" across consecutive breaches. Whether the configured rule authorizes dispatch on its own. Behaviour on missing or failed input. Behaviour on a failed send. Strict versus inclusive comparison. Whether a recovery notice is wanted. Audit owner.
