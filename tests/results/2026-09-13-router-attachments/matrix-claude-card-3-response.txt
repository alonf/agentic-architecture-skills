# Decision Card

Mode: Decision Card
Requirement: Every five minutes, compare a supplied numeric queue length with a configured threshold and send one alert through the existing notification service when exceeded; rule and destination are already configured. Not illustrative; taken verbatim from the request.
Known facts: Repository material is a single file, prompt.txt, which only restates the requirement; no code, configuration, or service contract is present. Requirement facts: fixed five-minute cadence; the queue length is supplied, not discovered; the threshold, rule, and destination exist; the notification service exists; exactly one alert per exceedance.
Unknown / assumptions: How the queue length is supplied and what happens on a missing sample; whether "one alert" means once per threshold crossing or once per tick while exceeded (de-duplication and hysteresis policy); strict versus inclusive comparison; who authorizes dispatch; audit owner; behaviour when the notification service fails. Nothing assumed. Not atomic: three responsibilities follow.
Routed mechanism: (1) Sample on schedule → deterministic code (timer). (2) Compare value with threshold → deterministic code. (3) Conditionally dispatch one alert → deterministic code calling the existing service. Bounded-AI challenge: a single fixed-shape model call could return the comparison, but the rule is fully specified and numeric, so deterministic code already satisfies it; verdict: no AI, therefore no agent. Workflow axis: a fixed scheduled sequence; a timer is sufficient and no orchestration engine is required.
Agent boundary: No agent is proposed, so the extra-agent boundary test does not apply. No MCP boundary: the existing notification service integration is retained, and no MCP-specific property such as standardized tool discovery across independent clients is stated or needed.
Evidence classification: Supplied queue length is structured application data (rung 2), or authoritative operational state (rung 1) if read live from the queue itself, which is unknown. Configured threshold, rule, and destination are organizational knowledge (rung 3). prompt.txt is a document (rung 4). Agent memory is not used. Retrieved knowledge is evidence about the system, not authority over what it must do.
Authority chain: Deterministic control boundary. Reasoning: fixed rule proposes an alert, with no model involved. Authorization: whether the configured rule and destination constitute dispatch authority, and the once-only policy, are unknown — governance decision required; a configured destination alone is not dispatch authority. Authoritative service: the existing notification service, owner unknown. Execution: one send call per authorized exceedance. Audit: recorded outcome of each send, owner unknown.
Rejected alternatives: all-deterministic: sufficient, and it is the chosen routing, because every input and rule is fixed and numeric; bounded-AI-only: insufficient in value, since it adds non-determinism and cost to a comparison that needs neither; agent-everywhere: could perform the comparison but grants run-time discretion over an alert the requirement fixes completely, at needless cost; multi-agent: no distinct security, context, deployment, ownership, model, or specialisation boundary exists, so no second agent is justified; workflow-only: sufficient, since a scheduled sequence of the fixed comparison and one service call covers the requirement with no agentic step.
Decision and trade-off: Generic mechanism: a scheduled deterministic rule with a control boundary in front of the notification send. No product is named, and no platform mapping is needed because no AI mechanism was selected. Outcome: fully testable, near-zero run cost, no model risk. Cost: none beyond a timer and one service call. Uncertainty: the meaning of "one alert" and the dispatch authorization policy are unresolved and must be decided before the send path is built.
**Architecture review required before implementation.**
