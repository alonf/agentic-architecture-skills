# Decision Card

Mode: Decision Card
Requirement: Every five minutes, compare a supplied numeric queue length with the configured threshold and send one alert through the existing notification service when it is exceeded; rule and destination are already configured.
Known facts: Repository material — the working directory holds only prompt.txt, which restates the requirement verbatim and contains no code, configuration, scheduler, notification-service contract, or instruction-shaped content (no surfaced conflict). Requirement — five-minute cadence; the queue length is supplied as a number; one threshold and one destination are pre-configured; exactly one alert per exceedance; the notification service already exists.
Unknown / assumptions: Source and freshness of the supplied queue length; whether "one alert" means once per tick or once per breach episode (which would need state across ticks); behaviour on a missing or stale sample; whether the configured rule alone authorizes dispatch; audit owner; scheduler host. Not atomic — three responsibilities: (1) sample on schedule, (2) compare number to threshold, (3) conditionally dispatch one alert.
Routed mechanism: All three responsibilities → **deterministic code**. Bounded-AI challenge: could one fixed-shape model call satisfy the comparison? It could, but a numeric comparison is a fixed rule that deterministic code already satisfies completely, with no semantic interpretation and no intermediate finding that changes the next step, so no bounded AI and no agent is justified. Workflow axis: a fixed scheduled sequence (timer → sample → compare → gated send); a plain scheduler suffices, and a durable workflow engine is needed only if breach-episode state must survive restarts (unknown).
Agent boundary: No agent proposed, so the agent-boundary gate does not apply. **No MCP boundary** — the existing notification-service integration is retained; no MCP-specific property (such as standardised tool discovery across independent clients) is stated or needed.
Evidence classification: Supplied queue length — structured application data (rung 2; rung 1 only if read live from the queue itself, source unknown). Configured threshold and destination — organizational knowledge held as configuration (rung 3). prompt.txt — documents (rung 4), restating the requirement only. Agent memory is not used. Retrieved knowledge is evidence about the system, not authority over what it must do.
Authority chain: Sending an alert is a consequential action, so a **deterministic control boundary** applies: reasoning — the fixed rule produces an alert proposal (no model involved) → authorization — whether the configured rule alone permits dispatch, and the one-alert de-duplication policy, are **unknown — governance decision required** (a configured destination is not dispatch authority) → authoritative service — the existing notification service (owner unspecified) → execution — one send call → audit — send outcome recorded (owner unknown).
Rejected alternatives: all-deterministic: sufficient, and chosen, because every responsibility is a fixed rule over supplied numbers; bounded-AI-only: insufficient as a choice, since it can compare but adds cost and non-determinism to a rule code already satisfies; agent-everywhere: could compare but grants run-time discretion over steps the requirement fixes, at needless cost and authority; multi-agent: no distinct security, context, deployment, ownership, model, or specialisation boundary exists, so unjustified; workflow-only: sufficient if it hosts the fixed comparison and the gated send, with no agentic step, and reduces to a scheduled job in its simplest form.
Decision and trade-off: Generic mechanism — a scheduled deterministic job: timer → read supplied sample → compare to configured threshold → policy-gated single send through the existing notification service → audit record. No AI, no agent, no MCP surface; product mapping is unnecessary and, if wanted, is delegated to the platform skill rather than asserted here. Cost is minimal and behaviour is fully testable. Uncertainty sits in the unresolved items: sample source and staleness handling, one-per-tick versus one-per-episode semantics, dispatch authorization policy, and audit ownership — all must be settled before build.
**Architecture review required before implementation.**
