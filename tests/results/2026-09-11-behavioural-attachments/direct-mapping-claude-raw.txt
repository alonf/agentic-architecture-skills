## Mapping: human sign-off on a consequential tool call

**Responsibility:** a specific, consequential tool call must pause and get human approval before it executes.

**Construct:** `ApprovalRequiredAIFunction` (construct-map.md row 9).

This is *per-call* authorization — the approval boundary sits on one function invocation, not on a graph transition. Don't reach for the workflow-graph human gate (row 8, `Microsoft.Agents.AI.Workflows` with a gate step) unless the requirement is really "pause at this specific *stage* of a fixed sequence," and don't reach for MCP elicitation (row 7) unless the tool call itself needs to ask the human a *question mid-execution* to get an argument value — that's a different pause-and-resume contract (protocol-layer, not authorization). Your case as stated — "this call runs only with sign-off" — is squarely row 9.

## Runtime/control placement

Per `runtime-and-control.md` row 7 (human authority), this repo's material distinguishes three authority layers by granularity, and picking the wrong one is the common mistake:

| Layer | Granularity | Construct |
|---|---|---|
| Workflow-level gate | one step in a fixed sequence | `Workflows` graph + gate (row 8) |
| **Per-tool-call approval** | **one function invocation** | **`ApprovalRequiredAIFunction` (row 9)** ← this decision |
| Delegated-access consent | acting *as* the calling user downstream | explicit consent flow (row 6) |

A workflow gate doesn't substitute for per-call approval, and neither substitutes for consent-to-act-as-user — name the layer explicitly rather than treating "human in the loop" as one undifferentiated fact.

Beyond that, the approval mechanism itself is orthogonal to hosting: whether the agent runs in-process or in a hosted runtime (row 1), the approval boundary still lives at the function-invocation layer, not the hosting layer. If hosted, the session's lifecycle (row 5) and isolation (row 4) don't change how the approval gate behaves — the agent doesn't control when its own session idles out, and that's independent of who has to approve this call.

## Assurance

- **Observe:** the approval request and its outcome (approved/denied, by whom, with what arguments) must be captured as execution evidence independent of the agent's own narration — this is explicitly called out in `assurance.md` as one of the things "observe" must capture (tool calls made, arguments passed, approvals requested and their outcome).
- **Evaluate:** check that sign-off was actually required and obtained before the call ran — not that the transcript merely mentions an approval.
- **Verify behaviour:** confirm the routing decision still holds — i.e., that this call is still being intercepted by the approval construct and hasn't drifted to firing without gating (a silent autonomy increase) as the design evolves.
- **Regress:** re-check this after later changes; an approval gate that isn't re-verified after a refactor is a historical record, not a live control.
