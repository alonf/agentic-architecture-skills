=== P4 : We already approved a fixed step sequence with one human authorization boundary. Where does the human approval go in Agent Framework? ===

**Responsibility → construct**

| Responsibility | MAF construct | Why |
|---|---|---|
| Fixed step sequence with one authorization boundary | `Microsoft.Agents.AI.Workflows` graph with a human gate at that step | Sequencing is deterministic, so the workflow graph owns control flow — not an agent deciding what's next. **Where exactly it goes:** the gate sits on the edge/transition *into* (or out of) the specific step you already scoped as the authorization boundary — the workflow pauses there, surfaces the pending state for human sign-off, and only advances to the next step once approved. - Delegated-access consent (`runtime-and-control.md` #6) — for acting *as* the calling user against a downstream system; not an approval-of-an-action mechanism at all.

Since you said "one human authorization boundary" at a specific point in the sequence, that's the workflow-graph gate (row 8), not the per-function approval.

=== P8 : The architecture decision is already approved: load procedural guidance only when relevant, not in permanent context. How do I build this with Agent Framework in C#? ===
This maps to a single row in the construct map — no multi-construct composition needed.

## Mapping

**Responsibility:** procedural guidance loaded only when relevant, not held in context permanently.

**Construct:** `AgentSkillsProvider`, backed by one or more `SKILL.md` files — construct-map.md row 5.

**Why this construct and not another:** the defining property is *progressive disclosure* — the guidance must cost zero context when its responsibility isn't in play for the current turn, and it must stay declarative content the provider injects, never code the agent executes directly. That rules out:
- putting it in the system prompt (permanent context — violates the approved decision directly),
- a plain `AIContextProvider`/`TextSearchProvider` (row 3) — that's for an external evidence corpus the agent cites, not procedural how-to content the agent follows,
- a custom memory-recall provider (row 4) — that's the agent's own prior findings, a different origin than authored procedural guidance.

## Wiring, at concept level

`AgentSkillsProvider` is registered on the `AIAgent` at construction time, the same way any context provider is composed into the agent's context-assembly step. Each `SKILL.md` stays a standalone declarative file (name, description, trigger conditions, body) — the provider is what inspects the current request and decides whether a given skill's content gets pulled into context for that turn, not the agent's own reasoning loop.

One sub-decision this doesn't resolve on its own: *how* the provider judges "relevant." If that judgment is a deterministic match (frontmatter keywords, path/tool-name triggers) it's plain code inside the provider; if it needs semantic judgment beyond keyword matching, that's itself a mechanism decision (bounded AI selection call vs. something requiring its own agent loop) that construct-map.md doesn't specify — worth a quick pass back through `agentic-architecture-router` only if your provider's matching logic turns out to need more than deterministic triggers.

## Runtime and control placement

Hosting placement isn't a separate decision here — the provider runs wherever the `AIAgent` itself runs (in-process or hosted runtime); it's part of context assembly at invoke time, not an independently hosted component. It doesn't touch isolation, lifecycle, estate control, or the three human-authority layers (runtime-and-control.md rows 4–7) — there's no approval boundary in loading declarative guidance. If a *specific skill's procedure* later includes a step that itself needs sign-off, that's a separate row-8/row-9 decision layered on top, not part of this mapping.

## Assurance

- **Observe:** capture which skill(s) were considered and which were actually injected per turn, independent of the agent's own narration of "I followed skill X."
- **Evaluate:** did the right skill load when the trigger condition was met, and — the harder direction — did it stay absent on unrelated turns? Progressive disclosure is falsifiable both ways.
- **Verify behaviour:** watch for the provider's relevance check quietly growing more autonomous than the trigger logic you actually built (e.g., a keyword match slowly turning into an implicit model judgment call nobody routed).
- **Regress:** re-check after adding new `SKILL.md` files that they don't get injected for requests they shouldn't match, and that existing triggers didn't shift.

## Open items to verify live before coding

`AgentSkillsProvider` and `SKILL.md` are named directly in construct-map.md without an "unsure" flag, but neither construct-map.md nor maf-surface.md carries a namespace, package version, or GA/preview status for it — maf-surface.md's checked-facts list doesn't cover this construct at all. === N14 : Give me a tutorial on Microsoft Agent Framework sessions vs memory vs knowledge. ===
# Sessions vs Memory vs Knowledge in Microsoft Agent Framework

These three get conflated constantly because they all look like "the agent remembers something." They're actually three different architectural concerns, distinguished by **where the content comes from** and **how long it lives**. Here's the breakdown, based on the demonstrated constructs from the Agent Framework material.

## The core distinction

| | Sessions | Memory | Knowledge |
|---|---|---|---|
| **What it holds** | Conversational state (turns, tool calls) | The agent's own prior findings/outcomes | An external evidence corpus |
| **Lifespan** | One interaction only | Across sessions | Persistent, independent of any session |
| **Origin of content** | Generated during this conversation | Generated by the agent in past conversations | Never generated by the agent — it's someone else's data |
| **Trust posture** | Authoritative for "what did we just say" | Treated as a *hypothesis to re-verify*, not a fact | Cited, not absorbed as if the agent already knew it |
| **Construct** | `AgentThread` (naming unconfirmed — see caveat below) | A custom `AIContextProvider` that recalls prior outcomes | `AIContextProvider` backed by a search source, e.g. `TextSearchProvider` |

## 1. Sessions — turn-to-turn continuity within one interaction

**Mechanism it satisfies:** "conversational state persisting across turns, within one interaction."

This is the narrowest of the three. It's what lets an agent remember message 3 said "use Python" when it's now processing message 7 of the *same conversation*. The defining property is negative: it must **not** survive the interaction ending, and it must not be conflated with recall across sessions — that's memory's job, not the session's.

> **Naming caveat:** the construct is commonly called `AgentThread`, but some current material refers to the persisted-session wrapper as `AgentSession`. Don't pick one from memory — confirm the current SDK name against live documentation before you write it into a design doc or code.

## 2. Memory — recall of the agent's own prior findings, across sessions

**Mechanism it satisfies:** "recall of the agent's own prior findings across sessions."

Memory is what a session deliberately isn't: it survives past one interaction. But the critical architectural rule is about *trust*, not just lifespan — content that comes back through memory originated from the agent's own past reasoning, and reasoning can be wrong. So memory should be surfaced to the agent as **something to re-verify**, not as an asserted fact the way a system prompt is. If you build memory recall that feeds prior conclusions back in as ground truth, you've built a mechanism that compounds its own past mistakes silently.

The construct is a **custom `AIContextProvider`** — there's no off-the-shelf "memory store" class; you write the provider that decides what to recall and how to frame it.

## 3. Knowledge — external evidence the agent cites, not memorizes

**Mechanism it satisfies:** "read access to an external evidence corpus the agent must cite, not memorise."

Knowledge is the odd one out because the content **never came from the agent at all** — it's a document store, a search index, a knowledge base someone else owns. Architecturally this is a retrieval/context-injection concern, kept deliberately separate from the agent's own reasoning loop, specifically so what was retrieved stays **attributable and citable** rather than getting absorbed into the response as if the model already knew it.

The construct is `AIContextProvider` backed by a search source — `TextSearchProvider` is the demonstrated example.

### A fourth thing that looks like knowledge but isn't: procedural knowledge (Skills)

There's a related-but-distinct mechanism worth knowing about here: **procedural knowledge loaded only when relevant, not held in context permanently** — i.e., "how do I do X" rather than "what is X." That maps to `AgentSkillsProvider` + a `SKILL.md`. The distinguishing property is **progressive disclosure**: the procedure shouldn't cost context tokens when it's not in play, and it must stay declarative content the agent reads — never executable code the agent runs directly. This is a sibling to the "cite an evidence corpus" pattern, not the same thing — don't reach for a search-backed `AIContextProvider` when what you actually need is a loaded-on-demand procedure.

## Why the boundaries matter (the failure mode this prevents)

The reason these three are kept as separate constructs rather than one generic "give the agent context" bucket:

- **Session leaking into memory**: if turn-scoped state quietly persists past the interaction, you get stale conversational context bleeding into unrelated future sessions.
- **Memory treated as knowledge**: if the agent's own past conclusion gets fed back in with the same trust weight as a cited external document, errors compound — the agent starts "citing" its own unverified prior guess as if it were sourced fact.
- **Knowledge treated as memory**: if retrieved documents get absorbed into the agent's apparent own knowledge instead of staying attributable, you lose the ability to say *why* the agent said something — no citation trail.

## Choosing between them for a given responsibility

Ask, in order:
1. Does this need to survive past the current interaction? No → session (`AgentThread`).
2. Yes — did the content originate from the agent's *own* past reasoning? Yes → memory (custom `AIContextProvider`, framed as re-verifiable).
3. No — does it come from an external corpus the agent should cite? Yes → knowledge (`AIContextProvider` + `TextSearchProvider`).
4. Is it actually a "how-to" procedure rather than factual content? → Skills (`AgentSkillsProvider` + `SKILL.md`), not knowledge.
