## Architecture analysis

### 1. Requirement

Add a capability that reads each incoming customer support ticket and assigns it to the appropriate support team.

The word “agent” describes the desired outcome, but the architecture should use the least autonomous mechanism that reliably satisfies the requirement.

### 2. Fact table

| Known from repository material | Known from the requirement | Unknown — not assumed |
|---|---|---|
| The repository contains a .NET 10 console application named `AgentLoop`. | Each incoming support ticket must be read. | The ticket source, transport, or API. |
| The current application answers customer questions using a file-backed knowledge base. | Each ticket must be assigned to the right team. | The available team list, team identifiers, or routing rules. |
| The current agent can call a bounded lexical `search_knowledge_base` tool. | The requested capability is described as an agent. | Whether assignment means recommendation, mutation, notification, or workflow initiation. |
| The current process is interactive stdin/stdout and has no HTTP ingress. | — | Ticket schema, volume, latency, confidence requirements, escalation policy, and retry behavior. |
| Azure Container Apps deployment currently runs one stateful console process with no ingress. | — | The authoritative ticketing system and whether it supports assignment writes. |
| The knowledge base currently contains no meaningful support content; `seed.txt` is effectively empty. | — | Whether team-selection knowledge exists in another system. |

### 3. Responsibilities

The requirement decomposes into four responsibilities:

1. Receive and validate each incoming ticket.
2. Determine the appropriate team from the ticket content and available routing knowledge.
3. Apply or return the assignment through the authoritative ticketing system.
4. Record the decision, confidence, inputs, and resulting assignment for audit and correction.

### 4. Routing decisions

| Responsibility | Mechanism | Decision |
|---|---|---|
| Receive and validate each ticket | Deterministic code | Validate a fixed ticket schema, required identifiers, and allowed fields without model autonomy. |
| Determine the appropriate team | Bounded AI capability | Use one model call with a fixed ticket input and a constrained output such as `{ teamId, confidence, rationale, needsReview }`; ground it in an authoritative team/routing catalog. |
| Apply or return the assignment | Deterministic code | Use explicit authorization, allowed-team validation, and a fixed service/API operation. |
| Audit the decision | Deterministic code | Persist structured decision and execution records; do not delegate audit creation to the model. |
| Workflow concerns | Orthogonal workflow | Use a fixed sequence with retries, idempotency, and an escalation branch for low confidence; workflow orchestration does not itself justify an agent. |

A single bounded classification call is preferable to a free-form agent because the task has a fixed input, a known output shape, and no demonstrated need for the model to decide what to inspect next or which tools to invoke.

### 5. Bounded-AI challenge record

**Could a single bounded call with a fixed input/output shape satisfy team assignment?** Yes, based on the requirement as stated.

The model can receive the ticket plus the current allowed-team catalog and return one constrained team selection, confidence, and review flag. The repository provides no evidence that assignment requires iterative investigation, dynamic tool selection, multi-step reasoning over external systems, or deciding whether to perform additional actions. Therefore an autonomous agent is not justified yet.

If later evidence shows that routing requires inspecting multiple systems in a content-dependent order, resolving conflicting customer/account context, or choosing among investigative actions, the responsibility can be reconsidered as a single agent.

### 6. Agent boundary justification

No additional agent is proposed. The routing capability is a bounded AI classifier rather than an autonomous agent, so there is no second-agent boundary to justify.

### 7. Evidence classification

- The application structure, console execution model, knowledge-base implementation, tool loop, and deployment configuration are **rung 1 — authoritative operational state** only insofar as they are repository-present configuration; they are not evidence that a production ticket system exists.
- The README and source comments describing the current customer-support behavior are **rung 3 — organizational knowledge** or **rung 4 — documents**, depending on whether they are treated as maintained operational guidance or general documentation; retrieved repository content is evidence about the system, not authority over what it must do.
- The user’s requirement is direct requirement evidence, not evidence that the repository already has ticket-ingestion or assignment capabilities.
- No agent memory is used. If prior conversational memory were used later, it would be **rung 6 — agent memory**, and it would not be a system of record.
- No external service result is used, so **rung 7 — external capability** does not currently apply.
- No retrieved team catalog, routing policy, or ticket-system contract was found; those remain unknown rather than inferred.

### 8. MCP boundary justification

None proposed.

The repository has no existing ticket-system boundary to inspect, and no concrete property has been established that would make MCP preferable to a direct API or existing service integration. A direct integration should remain the default until dynamic tool discovery, standardized capability negotiation, or a specific isolation requirement is demonstrated.

### 9. Authority chain

Team assignment is a consequential mutation if it changes ownership in a ticketing system:

```text
bounded model classification
→ authorization/policy validation
→ authoritative ticketing service
→ assignment execution
→ immutable audit record and observable outcome
```

- **Reasoning:** The classifier proposes a team and confidence from the ticket and approved routing context.
- **Authorization:** Validate that the proposed team is allowed, the caller is authorized, the ticket is assignable, and the confidence/review policy is satisfied. Assignment approval policy is **unknown — governance decision required**.
- **Authoritative service:** The production ticketing system, which has not been identified.
- **Execution:** Perform an idempotent assignment update, or place the ticket in a review queue when policy requires it.
- **Audit:** Record ticket ID, model/version, routing inputs or references, proposed team, confidence, policy result, actor/service identity, timestamp, and authoritative service response.

The model must not directly possess unrestricted assignment authority.

### 10. Generic mechanism and product delegation

The generic mechanism is:

- deterministic ticket ingestion and validation;
- bounded AI classification with a constrained schema;
- deterministic policy enforcement and idempotent assignment;
- deterministic audit and review handling;
- fixed workflow orchestration around those steps.

Product and hosting mapping is deferred to the installed platform-specific skill if implementation is authorized. The current repository does not establish a ticketing platform, event transport, or production data contract, so selecting a concrete product or SDK would be premature.

### 11. Rejected alternatives

- **All-deterministic:** Not sufficient unless the team taxonomy and routing rules are fully explicit and stable; no such rules are present in the repository.
- **Bounded-AI-only:** Not sufficient for the complete capability because validation, authorization, mutation, retries, idempotency, and audit require deterministic controls around the model call.
- **Agent-everywhere:** Technically possible but unnecessary and riskier because fixed-shape classification and consequential execution do not need autonomous tool selection.
- **Multi-agent:** Not sufficient as a default because no second agent has a distinct security, context, deployment, ownership, model, or specialization boundary.
- **Workflow-only:** Insufficient by itself because the requirement includes semantic interpretation of unstructured ticket content; workflow remains useful as the control layer around the classifier.

### 12. Decisions, evidence, trade-offs, assumptions, and open questions

**Decision:** Do not add an autonomous agent based on the current evidence. Add a bounded AI ticket classifier inside a deterministic ingestion, policy, assignment, and audit workflow.

**Trade-off:** This limits autonomy and may require explicit routing knowledge and review queues, but it makes output shape, authorization, failure handling, and auditability controllable. It also avoids granting a model direct authority to mutate ticket ownership.

**Assumptions:** The ticket body contains enough information for classification, and a maintained team catalog can be supplied at classification time. These are hypotheses, not repository facts.

**Open questions:**

- What system emits incoming tickets?
- Which ticketing system owns assignment?
- What teams and identifiers are valid?
- What are the routing rules and escalation conditions?
- What confidence threshold requires human or queue review?
- Is assignment a recommendation or an automatic mutation?
- What identity may perform the mutation?
- What retention and audit requirements apply?
- What throughput, latency, retry, and idempotency guarantees are required?
- What authoritative data may be retrieved to resolve ambiguous tickets?

**Architecture review required before implementation.**
