# Architecture analysis — support-ticket team assignment

Short version up front: **this does not need an agent.** The responsibility that involves AI is a single classification — ticket text in, one team from a fixed list out — and the bounded-AI challenge is satisfied by one fixed-shape model call. Everything around it (ingest, gate, write, audit) is deterministic. The skill stops before implementation, so I have not written code; the sections below are the decision and what has to be answered before building.

## 1. Requirement

For every incoming support ticket, determine which team should own it and assign it to that team.

## 2. Fact table

| Known from repository material | Known from the requirement | Unknown — not assumed |
| --- | --- | --- |
| The repo is `AgentLoop`: a .NET 10 console REPL running an autonomous tool-calling loop over the Anthropic C# SDK 12.47.0 (`AgentLoop/Agent.cs:54`, `AgentLoop/AgentLoop.csproj`). | Tickets arrive continuously ("each incoming"). | Where tickets come from (helpdesk API, mailbox, queue, form). |
| Its system prompt makes it a *coding* agent with `read_file`, `list_files`, `run_command` tools (`AgentLoop/Program.cs:14`, `:60`). | Input is a ticket; output is one team. | The ticketing system and how "assign" is expressed in it (field write, label, queue move). |
| `run_command` is gated by a **console** `[y/N]` prompt (`AgentLoop/Program.cs:67`, `AgentLoop/ConsoleApprovalHandler.cs:12`). | The set of teams is fixed (a ticket is assigned to "the right" one, implying a known list). | The team list, its size, who owns it, and where it is stored. |
| The loop allows up to 50 model calls per turn (`AgentLoop/AgentOptions.cs:12`), adaptive thinking, effort `xhigh` (`AgentLoop/Agent.cs:120-121`). | — | Assignment policy: auto-assign, or suggest for human confirmation; confidence threshold; what happens to ambiguous tickets. |

No illustrative content is used in this table. *Hypothesis* items below are labelled as such.

## 3. Responsibilities

Not atomic — six responsibilities:

- **R1 Ingest** — observe each new ticket and trigger processing exactly once.
- **R2 Normalise** — extract subject/body/structured fields, strip HTML/signatures/quoted history, bound length.
- **R3 Determine team** — map normalised ticket content to one member of the fixed team set.
- **R4 Assign** — write the assignment into the ticketing system.
- **R5 Handle uncertainty and failure** — low-confidence result, model error, or unknown team → fallback path.
- **R6 Audit and feedback** — record what was decided, why, and any later human re-assignment.

## 4. Routing decisions

| Responsibility | Mechanism | Reasoning (routing order: deterministic → bounded AI → agent → multi-agent) |
| --- | --- | --- |
| R1 Ingest | **Deterministic code** | Webhook/queue/poll consumer with idempotency on ticket id. Nothing content-dependent. |
| R2 Normalise | **Deterministic code** | Fixed parsing rules. *Hypothesis*: if tickets carry a structured product/category field that maps 1:1 to a team, a deterministic pre-route can short-circuit R3 for those. |
| R3 Determine team | **Bounded AI capability** | Deterministic rules fail on unstructured free text. A single call with fixed input (ticket text + team catalogue) and fixed output shape (team id from a closed set, confidence, one-line rationale) satisfies it. Agent rejected — see §5. |
| R4 Assign | **Deterministic code** (consequential — §9) | A write via the ticketing system's existing API. No decision is made here; the decision was R3 filtered by policy. |
| R5 Uncertainty/failure | **Deterministic code** | Threshold compare + route to a default triage queue; retry on transient API errors. The threshold value is a governance input, not a code decision. |
| R6 Audit | **Deterministic code** | Append-only record. |

**Workflow axis (orthogonal):** a fixed, linear per-ticket pipeline R1→R2→R3→R5-gate→R4→R6 with retry on transient failure and idempotency per ticket. No step decides what the next step is, so no agentic step exists inside the workflow. Whether this needs a workflow *engine* versus a plain queue consumer with retry depends on volume/durability requirements — unknown.

## 5. Bounded-AI challenge record

**R3 — "Could a single bounded call with a fixed input/output shape satisfy this responsibility?"**
**Yes.** The input is fully known before the call (normalised ticket + team catalogue with short descriptions). The output is one label from a closed set plus confidence. There is no intermediate finding that changes what to examine next, in what order, or whether another step is needed — the call examines the ticket once and answers. Complexity of the text and the fact that it is natural language are not, per the framework, reasons the challenge fails.

**Consequence:** no responsibility is routed to an agent. Specifically, the existing `Agent` loop in this repo is the wrong construct for R3 — it grants the model run-time control over which files to read and which shell commands to run, which the responsibility never needs, and it would place untrusted ticket text in front of a `run_command` tool (see §7, content-as-evidence).

**n/a** — zero agents proposed, so no boundary needs justifying.

## 8. MCP boundary justification

**None proposed.** The ticketing system's existing API is the boundary for R1 and R4; the classifier is one in-process call. No property that only MCP provides (dynamic tool discovery across untrusted hosts, a specific isolation guarantee, standardised capability negotiation) is needed here.

## 9. Authority chain

**Consequential operation: R4 — writing an assignment into a customer-facing ticketing system.**

```text
reasoning        R3 bounded classification → {team id, confidence, rationale}   (rung 7 — a proposal)
authorization    unknown — governance decision required
                 (auto-assign above a threshold? suggest-only pending human confirmation? who may override?)
                 Note: the repo's ConsoleApprovalHandler (a stdin [y/N] prompt) is not a usable
                 authorization mechanism in an unattended pipeline.
authoritative    the ticketing system owns assignment state; the classifier owns nothing
execution        deterministic, idempotent write via the ticketing system's existing API
audit            ticket id, model + prompt version, catalogue version, output, confidence,
                 policy outcome, and any subsequent human re-assignment (feeds accuracy measurement)
```

**Second consequence to name:** R3 sends ticket content — plausibly containing customer PII — to an external model API. Whether that is permitted, and under what residency/redaction rules: *unknown — governance decision required*.

## 10. Generic mechanism and product delegation

**Generic mechanism:** event-driven per-ticket pipeline; deterministic ingest and normalise; **one bounded, constrained-output classification call** against a closed, versioned team catalogue; deterministic confidence gate with a triage fallback; deterministic assignment write through the existing ticketing API; append-only audit.

**Product mapping:** deferred. `maf-architecture-mapping` is installed but targets Microsoft Agent Framework, which this repo does not use; the repo is built directly on the Anthropic C# SDK, so the applicable platform reference for the single classification call is the `claude-api` skill — to be loaded at implementation time, after review. No SDK-level detail is asserted here from memory. The one repo-level architectural statement I will make: the classifier should be a new, separate single-call path, **not** a new tool set or system prompt bolted onto the existing `Agent` loop.

## 11. Rejected alternatives

- **All-deterministic** — insufficient: ticket text is unstructured and a keyword/rule table would not generalise; a deterministic pre-route for structured fields is worth keeping only as an optional short-circuit (*hypothesis*).
- **Bounded-AI-only** — insufficient as the *sole* mechanism: only R3 needs a model, and using model calls for ingest, gating, the write, or audit would add nondeterminism where a rule suffices — but this is the closest alternative to the chosen routing, which uses exactly one bounded call and nothing more autonomous.
- **Agent-everywhere** — not justified: no responsibility needs to decide what to examine next; it would cost latency, up to 50 model calls per ticket, non-reproducible outcomes, and — with the existing tool set — a prompt-injection surface from untrusted ticket text into `run_command`.
- **Multi-agent** — not justified: no responsibility needs even one agent, so no security/context/deployment/ownership/model/specialisation boundary exists for a second.
- **Workflow-only** — insufficient alone: an orchestration layer cannot produce a team label from free text; but the workflow axis is where this design lives — a fixed pipeline wrapping the one bounded call.

## 12. Decisions, evidence, trade-offs, assumptions, open questions

**Decisions.** No agent. One bounded classification call with a closed output set. Everything else deterministic. Assignment is a consequential write with an authorization policy that is currently unspecified.

**Evidence relied on.** Repository as-built code and IaC (rung 3); the requirement (rung 4); the skill's counter-example as a cross-check (rung 3, evidence not authority).

**Trade-offs accepted.** A bounded call cannot ask a clarifying question or look up the customer's account before deciding — acceptable because the requirement asks for a label, not an investigation. If a future requirement becomes "check the customer's plan and recent incidents, *then* decide", re-run the bounded-AI challenge; that shape may fail it. Accuracy is bounded by the quality of the team catalogue descriptions. The confidence gate trades automation coverage for safety on ambiguous tickets.

**Assumptions (labelled).** *Hypothesis*: the team set is closed and small enough to pass as call input. *Hypothesis*: volume does not require a distributed workflow engine. *Hypothesis*: tickets are primarily text.

**Open questions — to answer before implementation.**
1. Ticket source and trigger mechanism.
2. Ticketing system, its API, and what "assign" means in it.
3. Team catalogue: contents, owner, storage, versioning.
4. Assignment policy: auto vs. suggest, confidence threshold, override rights.
5. PII / data-residency policy for sending ticket text to the model API.
6. Languages, latency SLA, expected volume.
7. Whether the existing no-ingress console deployment is the intended host — its shape does not fit a service that reacts to incoming tickets.

**Architecture review required before implementation.**

## 3. Responsibilities

The requirement is not atomic. It decomposes into five:

1. **Answer generation** — given a question and relevant knowledge-base content, produce a grounded answer.
2. **Retrieval** — given a question, find the relevant knowledge-base passages.
3. **Ingestion / indexing** — turn the knowledge base into something retrievable (offline, ahead of any question).
4. **Unanswerable handling** — when nothing relevant is found, do not fabricate; take the fallback path.
5. **Delivery** — receive the customer's question from a channel and return the answer to it.

## 4. Routing decisions

Routing order: deterministic code → bounded AI capability → single agent → multi-agent. Workflow evaluated separately below.

| # | Responsibility | Routed to | Reasoning |
| --- | --- | --- | --- |
| 1 | Answer generation | **Bounded AI capability** | Fixed input (question + retrieved passages [+ history]), fixed output (answer + citations + "answerable" flag). Deterministic code is insufficient: synthesising a natural-language reply from free-text passages is not rule-based. Nothing about the call's shape changes per question. |
| 2 | Retrieval | **Deterministic code** | A query against an index returning top-k passages is a lookup. An optional bounded AI call could rewrite the query first; it does not change the routing. |
| 3 | Ingestion / indexing | **Deterministic code** | Chunk, normalise, index. If a vector index is chosen, the embedding step is a bounded AI capability (fixed text → fixed vector) inside an otherwise deterministic batch pipeline. |
| 4 | Unanswerable handling | **Deterministic code** | A retrieval-score threshold gate *before* generation; the bounded call's prompt additionally constrains it to the supplied context. The *escalation* action, if in scope, is consequential — see §9. |
| 5 | Delivery | **Deterministic code** | Transport in/out of a channel. Note the repo's current process has no ingress and reads stdin; the channel is unknown (§2). |

**Workflow axis (orthogonal):** a fixed linear sequence — receive → retrieve → threshold gate → generate → deliver. No branching decided by content, no saga, no compensations. Plain sequential code; no workflow engine. Ingestion is a separate offline batch run on the knowledge base's update cadence.

**No agent is selected.** The existing `Agent` class makes an agentic shape (register a `search_knowledge_base` tool, let the model decide when to search) trivially cheap to build. Availability of the loop is not evidence that the responsibility needs it.

## 5. Bounded-AI challenge record

Run for responsibility 1, the only candidate for an agent:

> *Could a single bounded call with a fixed input/output shape satisfy "answer a customer question from the knowledge base"?*

**Yes.** Retrieve, then generate, is a fixed pipeline: the retrieval step is executed, not decided, and what it returns does not change *which steps* run next — only the content of the generation call. There is no "examine this, then decide what to examine next" step for single-hop questions.

**Recorded escalation condition** (not assumed to hold): if evaluation on real customer questions shows that a material fraction need a *second* retrieval whose query is determined by the first result (e.g. a passage says "see the refund policy", which is a different document), then intermediate findings do determine the next step and responsibility 1 escalates to **single agent** — at which point the existing `Agent` loop with one `search_knowledge_base` tool is the right shape. That is a measured finding, not a design default.

## 9. Authority chain

Two consequential operations exist, and routing away from an agent does not remove the chain requirement:

**A. Sending an answer to a customer** (customer-facing action)
- Reasoning: the bounded call's output (answer + citations + answerable flag)
- Authorization: **unknown — governance decision required** (auto-send vs. human review before release; the requirement does not say)
- Authoritative service: the customer channel — unknown (§2)
- Execution: message delivered
- Audit: log question, retrieved passage IDs, answer, model ID, usage, and the answerable flag — sufficient to reconstruct any answer after the fact

**B. Escalating / handing off** when the threshold gate fails (only if escalation is in scope)
- Reasoning: deterministic gate result (no passage above threshold)
- Authorization: **unknown — governance decision required**
- Authoritative service: unknown (ticketing, human queue)
- Execution / audit: as above

Reading the knowledge base is not consequential; no chain needed.

## 10. Generic mechanism and product delegation

**Generic mechanism:** a deterministic retrieval pipeline over an indexed knowledge base, a deterministic relevance threshold gate, one bounded generation call with a fixed output shape (answer, citations, answerable flag), and deterministic delivery. Ingestion is an offline deterministic batch, optionally with a bounded embedding step.

**Implication for this codebase (mechanism-level, not product):** the routed shape does not need the tool loop. It is a new thin answerer that makes one model call, reusing the existing `IAnthropicClient` registration, `AgentOptions`-style configuration, and cached system prompt — not a new `AgentTool` on the existing `Agent`.

**Product delegation:** the repo uses the Anthropic C# SDK directly, so `maf-architecture-mapping` (Microsoft Agent Framework) is not the fit. API-level specifics — the exact call shape, whether the SDK offers a citations feature or a server-side search tool that could collapse retrieval into the call, and whether an embedding provider is available under the Anthropic SDK or must come from elsewhere — are **delegated to the installed `claude-api` skill at implementation time** and are not asserted here from memory.

## 11. Rejected alternatives

- **All-deterministic:** insufficient — retrieval, gating, and delivery are rule-based, but producing a natural-language answer from free-text passages is not.
- **Bounded-AI-only:** **sufficient — this is the chosen routing**; one bounded generation call, everything else deterministic.
- **Agent-everywhere:** insufficient justification — retrieval, gating, and delivery never decide what to examine next; the cost would be added latency, token spend, unbounded retrieval loops, and a harder evaluation story, with no quality gain on single-hop questions.
- **Multi-agent:** insufficient justification — zero agents are proposed, so no boundary exists to justify a second one.
- **Workflow-only:** insufficient alone — sequencing retrieve → generate → deliver cannot produce the answer without the bounded generation step, and the sequence is simple enough that plain code is the workflow.

## 12. Decisions, evidence, trade-offs, assumptions, open questions

**Decision:** not an agent. A retrieve → gate → generate → deliver pipeline with exactly one bounded model call, built beside — not on top of — the existing `Agent` loop. Escalate to a single agent only if measured multi-hop demand triggers the condition in §5.

**Evidence:** repository source (rung 3), dev-machine SDK version (rung 1), knowledge-base content at run time (rung 3/4, evidence not authority), conversation history if enabled (rung 6, not a system of record), the model (rung 7).

**Trade-offs accepted:** cheaper per question, lower latency, predictable behaviour, and a fixed output shape that can be evaluated against a golden question/answer set. Less capable on multi-hop questions until the escalation condition is met and acted on.

**Assumptions (labelled):**
- *Hypothesis:* most customer questions are single-hop, answerable from one retrieval.
- *Hypothesis:* the knowledge base is text that can be chunked and indexed.
- *Hypothesis:* the console REPL is not the customer channel; a real channel will be added, which also means the "no ingress" deployment changes.
