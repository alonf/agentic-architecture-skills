## Mapping coverage

**Scope:** Step 2 of the MAF mapping procedure, assuming the mechanism decision is already approved. The twelve rows describe the responsibilities the construct map covers; they do **not** mean every approved architecture must use all twelve.

| # | Responsibility | MAF construct | Coverage status and evidence limit |
|---:|---|---|---|
| 1 | Runtime-directed investigation by one agent | `AIAgent` with a bound C# tool | **Demonstrated.** The material stages a single agent deciding what to check next. The adapterΓÇÖs exact API surface is dated separately and must be re-verified. |
| 2 | Conversation state within one interaction | `AgentSession` | **Demonstrated.** The evidence supports turn continuity, not durable cross-session memory. |
| 3 | External evidence retrieval and citation | `AIContextProvider` backed by a search source such as `TextSearchProvider` | **Demonstrated.** This covers retrieval/context injection, not memorized knowledge. |
| 4 | Recall of the agentΓÇÖs own prior findings | Custom `AIContextProvider` | **Demonstrated.** Prior findings are hypotheses requiring re-verification; this is distinct from external-corpus retrieval. |

| 6 | Independently owned tool surface with an approved MCP-specific rationale | `McpClient` against an MCP server | **Demonstrated.** Ownership alone is insufficient; without the separately approved MCP property, the mapping is a function tool over the existing typed API. |

## Named but not demonstrated

These are **not covered by a staged demonstration**, even though the source material names or compares them:

- **Handoff:** slide-only/not implemented in the demonstration. It is a workflow orchestration mode, not evidence that the staged system uses handoff.
- **Group chat:** slide-only/not implemented. Its current C# builder name remains unasserted and must not be inferred from another orchestration.
- **Harness agent:** named on a slide, but not implemented or demonstrated.
- **Governance middleware:** not demonstrated as middleware. The demonstrated authority mechanisms are the workflow gate, per-call approval, and delegated-access consent flow.
- **Protocols as a standalone construct:** not a separate demonstrated runtime construct; protocol choices are treated as ingress, negotiation, and binding decisions.

## Runtime/control coverage

For any selected row, the mapping still needs the Step 3 decisions: in-process versus hosted placement, ingress contract, protocol/binding negotiation, isolation, lifecycle control, identity propagation, and the applicable human-authority layer. A propagated caller identifier is not evidence of permission to act as that caller; delegated access requires explicit consent.

## Assurance and evidence limits

The mapping does not prove that an implementation satisfies its requirement. Step 4 requires independent execution evidenceΓÇötool calls, arguments, intermediate results, approval requests and outcomesΓÇöfollowed by requirement-specific evaluation, verification that the original routing decision still holds, and regression after changes.

No method signatures, namespaces, package versions, GA/preview claims, or current availability claims are established here. The surface notes contain dated facts that must be checked against current Microsoft Agent Framework documentation before implementation or a final platform design. No harness, middleware implementation, group-chat demonstration, or A2A wire compatibility should be inferred from this coverage.
