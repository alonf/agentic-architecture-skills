Every five minutes, compare a supplied numeric queue length against a configured threshold. When the threshold is exceeded, send one alert through the existing notification service. The rule and destination are already configured.

**3. Responsibilities**
The requirement is not atomic. Three responsibilities:

- **R1, sample on schedule.** Every five minutes, obtain the supplied queue length.
- **R2, evaluate the rule.** Compare the number to the configured threshold and produce a boolean.
- **R3, dispatch conditionally with single-alert semantics.** When the rule fires and no alert is already outstanding, call the notification service once, and record that state so the next sample does not re-send.

**4. Routing decisions**

- **R1 routes to deterministic code.** A timer and a read of a supplied value. Nothing about what to do next depends on content the code has not already been given.
- **R2 routes to deterministic code.** A numeric comparison against a configured value is a fixed computation with no semantic interpretation.
- **R3 routes to deterministic code.** A conditional call plus a persisted flag. The "one alert" rule is a state machine with two states, fully specified once the open question about re-arming is answered.

Workflow axis, evaluated separately: this is a fixed scheduled sequence of three steps with no branching beyond one boolean. A scheduler is needed. A separate workflow engine is not.

**9. Authority chain**
Sending an alert is a consequential operation. It pages or notifies someone. The chain:

```text
rule evaluation (deterministic, no model reasoning)
  -> authorization: the configured rule and destination; whether the configured
     rule itself constitutes dispatch authority is unknown ΓÇö governance decision required
  -> authoritative service: the existing notification service
  -> execution: one send call
  -> audit: owner unknown ΓÇö governance decision required
```

A configured destination is not by itself dispatch authority. The control boundary here is trivial because no model proposes anything, but it still exists: the code that decides to send must check the outstanding-alert state before calling the service.

**10. Generic mechanism and product delegation**
Generic mechanism: a scheduled deterministic job holding one piece of persisted state, the outstanding-alert flag, and calling the existing notification service. No AI mechanism of any rung is involved.

The `maf-architecture-mapping` skill is installed, but it maps agentic constructs. There is no agent, bounded call, or workflow-with-agent to map, so nothing is delegated and the analysis stops at the generic mechanism.

**11. Rejected alternatives**

- **All-deterministic:** sufficient, and it is the chosen routing.
- **Bounded-AI-only:** could return the comparison, but adds nondeterminism, latency, and cost to a rule that has no semantic content, so it is unnecessary and worse.
- **Agent-everywhere:** an agent could compare two numbers and call the service, but it would be granted authority to decide whether and how to alert, which the requirement never asks for.
- **Multi-agent:** no responsibility needs even one agent, so no second agent can name a distinct security, context, deployment, ownership, model, or specialisation boundary.
- **Workflow-only:** a scheduler running the fixed three-step sequence with no agentic step is sufficient, and it is effectively what the chosen routing is.

**12. Decisions, evidence, trade-offs, assumptions, open questions**

Decision: build a scheduled deterministic job. Do not build an agent, and do not add a model call.

Evidence relied on: the requirement text at rung 4 and the router's guidance document at rung 3. No runtime source was observed.

Trade-off accepted: the job cannot handle anything the rule does not already describe, such as a rapidly oscillating queue or a corrupted sample. That is the correct trade. Those cases are policy decisions to be encoded as rules, not judgment to be delegated to a model.

Assumptions, labelled: none were needed to reach the routing. The routing holds under every answer to the open questions.

Open questions the requirement left unanswered:

- Re-arm policy for "one alert". Does the alert clear when the value drops below the threshold, after a fixed time, or only manually?
- Strict versus inclusive comparison.
- Behaviour on a missing, stale, or non-numeric sample. Silent skip, or a separate alert?
- Whether the configured rule is the authorization to dispatch, or whether another policy gate applies.
- Retry and idempotency for a failed notification call.
- Audit owner and where sent alerts are recorded.
