## Runtime, control and assurance (steps 3 and 4)

- **Hosting placement is not in the supplied decision.** The construct is identical in-process or hosted. In-process, the typed client is an ordinary dependency. Hosted, the per-session sandbox needs network egress to the other team's API and a credential inside it.
- **Identity against the log API must be decided.** A service identity with read scope is the simplest fit. If the log API authorises per user, acting as the operator needs an explicit delegated-access consent step, because a propagated identifier is not a grant.
- **Human authority: none of the three layers applies.** No workflow gate, no per-call approval, and consent only if the identity question above resolves to acting-as-user. Record this as a decision, not an omission.
- **Lifecycle.** If hosted, one investigation must complete within the runtime's idle and reclaim policy, which the agent does not control.
- **Observe** every tool call at the tool boundary with arguments and responses, independent of the agent's narration.
- **Evaluate** against a set of previously failed jobs with known causes, since that is the requirement the agent was routed for.
- **Verify behaviour** in three directions. If traces show the same call sequence every run, the responsibility is over-routed and goes back to the router. If a second consumer appears or the contract starts changing independently, the no-MCP ruling must be revisited. Confirm the bound surface has stayed read-only.
- **Regress** on the other team's releases. Compile-time typing catches shape changes but not semantic ones such as a changed log format.
